## a. 引言

### a.1 目的

本文档旨在对“校园互助服务平台”进行完整、准确的软件需求定义，明确系统应实现的功能、性能指标、接口要求以及各类约束条件。本文档将作为以下工作的依据：

- 项目开发团队进行系统设计与编码实现的基准
- 测试团队制定测试计划和测试用例的依据
- 项目管理人员进行进度跟踪和质量控制的参考
- 用户和利益相关方验收系统的标准

### a.2 文档约定

- **优先级定义**：每条功能需求均标注优先级，分为“高”“中”“低”三档。高优先级为核心功能，须在第一阶段实现；中优先级为重要功能，须在第二阶段实现；低优先级为增强功能，可在后续版本迭代中实现。
- **需求编号规则**：功能需求采用“FR-模块缩写-序号”格式编号（如 FR-USER-001），非功能需求采用“NFR-类别-序号”格式编号。
- **术语约定**：本文档中使用的“应”“必须”表示强制性需求，“宜”“建议”表示推荐性需求。

### a.4 产品的范围

本产品是一个面向高校大学生的校园互助服务平台，旨在通过移动端应用（支持 iOS/Android App 及微信小程序）为学生提供一站式的互助服务。平台支持学生发布和接单各类互助需求，涵盖快递代取、学习辅导、二手交易、组队匹配等核心场景，通过实名认证和信用评价体系构建可信的校园互助生态。

平台的目标包括：

1. 整合校园内分散的互助需求信息，打破微信群、QQ 群等信息孤岛
2. 提高供需匹配效率，缩短需求响应时间
3. 通过信用体系保障交易安全和互助质量
4. 促进校园资源共享，营造互助友爱的校园氛围

本产品为独立系统，不替代任何现有校园信息系统，但预留与学校统一身份认证系统对接的接口。

## b. 综合描述

### b.1 产品的前景

当前，高校学生的校园生活中存在大量的互助需求：取快递排长队、外卖无人代拿、闲置物品无处处理、寻找学习搭档困难等。传统的互助方式主要依赖微信群、QQ 群、朋友圈等渠道，存在信息分散易遗漏、供需匹配效率低、缺乏信任保障机制等痛点。

校园互助服务平台正是为解决上述痛点而设计的新型产品。它整合了校园内各类互助需求，通过分类管理、智能推荐、信用评价等机制，构建一个安全、高效、可信的校园互助生态系统。平台采用“需求发布-精准匹配-安全交易-信用管理”的一体化架构，适配大学生学习、生活、社交等多元互助场景。

本产品可独立部署运营，也可与学校现有信息化系统集成，成为智慧校园的重要组成部分。

### b.2 产品的功能

平台的核心功能概述如下（详细功能需求见第 d 章）：

| 序号 | 功能模块 | 功能概述 |
|------|----------|----------|
| 1 | 用户认证与账户管理 | 支持校园统一身份认证、实名注册、个人资料管理、信用积分体系 |
| 2 | 需求发布与管理 | 支持按类型分类发布需求，标注详情、时间、地点、报酬等，支持编辑与撤销 |
| 3 | 智能匹配与推荐 | 基于需求类型、地理位置、用户标签自动推荐供需双方 |
| 4 | 在线沟通 | 提供内置即时通讯功能，支持图文交流与文件传输 |
| 5 | 交易保障 | 针对有偿互助提供担保支付、订单跟踪功能 |
| 6 | 信用评价体系 | 互助完成后双方互评，生成信用评分，关联账号权限 |
| 7 | 资源共享 | 允许学生上传学习资料、技能教程等，实现无偿分享 |
| 8 | 管理员后台 | 内容审核、用户管理、纠纷调解、数据统计与系统运维 |

## c. 外部接口需求

### c.1 用户界面

#### c.1.1 设计原则

- **简洁直观**：界面设计应符合大学生审美习惯，操作流程不超过 3 步即可完成核心功能
- **响应式布局**：适配不同尺寸的手机屏幕，确保界面元素在各分辨率下正常显示
- **一致性**：同类功能的交互模式保持一致，降低学习成本
- **即时反馈**：所有操作应有明确的状态反馈（如加载提示、成功/失败提示）

#### c.1.2 关键页面需求

| 页面 | 核心元素 | 说明 |
|------|----------|------|
| 首页 | 功能入口（四大模块）、需求动态流、搜索栏、发布按钮 | 展示附近的最新需求，支持按类型筛选 |
| 需求详情页 | 需求描述、发布者信息、报酬/价格、位置地图、沟通/接单按钮 | 完整展示需求信息，提供核心操作入口 |
| 发布页 | 分类选择、表单填写（文字/图片/位置/报酬）、发布按钮 | 支持多类型需求的统一发布入口 |
| 消息页 | 会话列表、即时通讯界面、系统通知 | 集成在线沟通功能 |
| 个人中心 | 用户信息、信用积分、我的需求/接单、设置、帮助中心 | 用户信息管理入口 |

本系统为纯软件系统，无直接硬件接口需求。

## d. 系统特性

### d.1 特性一：用户认证与账户管理

#### d.1.1 说明与优先级

**优先级**：高

用户认证是平台的入口和信任体系的基础，必须首先实现。通过校园统一身份认证保障用户真实性，建立信用基石。

#### d.1.2 激励/响应序列

1. 用户打开 App/小程序，进入登录/注册页面
2. 用户选择“校园认证登录”，跳转至学校统一身份认证页面
3. 用户输入学号和密码完成认证
4. 系统获取用户基本信息（姓名、学号、院系），自动创建/关联平台账户
5. 系统返回登录成功状态，进入首页
6. 用户可在个人中心完善资料（头像、昵称、联系方式等）

#### d.1.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-AUTH-001 | 系统应支持通过学校统一身份认证系统进行登录注册，用户无需额外设置密码 | 高 |
| FR-AUTH-002 | 系统应在用户首次登录时自动获取学号、姓名、院系等基本信息，并加密存储 | 高 |
| FR-AUTH-003 | 系统应支持用户编辑个人资料，包括头像、昵称、联系方式、个人简介等 | 中 |
| FR-AUTH-004 | 系统应支持用户设置隐私选项，控制个人信息的可见范围 | 中 |
| FR-AUTH-005 | 系统应支持用户查看自己的信用积分和信用等级 | 高 |
| FR-AUTH-006 | 系统应记录用户登录日志，包括登录时间、设备信息、IP 地址 | 中 |
| FR-AUTH-007 | 用户敏感信息（真实姓名、学号）必须使用 AES-256 加密后存储 | 高 |

### d.2 特性二：需求发布与管理

#### d.2.1 说明与优先级

**优先级**：高

需求发布是平台的核心功能，用户通过发布需求发起互助请求，是供需匹配的数据来源。

#### d.2.2 激励/响应序列

1. 用户点击首页“发布”按钮，进入发布页面
2. 用户选择需求类型（快递代取/学习辅导/二手交易/组队匹配）
3. 系统根据所选类型展示对应的表单
4. 用户填写需求详情、期望时间、地点、报酬（可选）、上传图片（可选）
5. 用户点击“发布”按钮提交
6. 系统进行内容审核（敏感词过滤）
7. 审核通过后需求发布成功，系统推送至匹配池
8. 用户可在“我的发布”中查看、编辑或撤销已发布的需求

#### d.2.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-DEMAND-001 | 系统应支持用户按类型分类发布需求，类型至少包括：快递代取、学习辅导、二手交易、组队匹配、其他代办 | 高 |
| FR-DEMAND-002 | 系统应支持用户为需求设置标题、详细描述、期望时间、地点标签、报酬金额（可为 0） | 高 |
| FR-DEMAND-003 | 系统应支持用户上传最多 9 张需求相关图片 | 中 |
| FR-DEMAND-004 | 系统应自动对发布内容进行敏感词过滤，识别违规内容并拒绝发布 | 高 |
| FR-DEMAND-005 | 系统应支持用户编辑已发布的需求（未被接单时） | 中 |
| FR-DEMAND-006 | 系统应支持用户撤销已发布的需求，若已产生交易需按规则处理 | 中 |
| FR-DEMAND-007 | 系统应支持用户按状态（进行中/已完成/已取消）查看自己的历史需求记录 | 高 |
| FR-DEMAND-008 | 系统应支持需求发布时标注位置信息，并基于校园地理范围进行定位校验 | 高 |

### d.3 特性三：智能匹配与推荐

#### d.3.1 说明与优先级

**优先级**：中

智能匹配提升供需对接效率，缩短需求响应时间。该特性依赖用户数据的积累和算法优化。

#### d.3.2 激励/响应序列

1. 用户发布需求后，系统将需求加入匹配池
2. 系统分析需求类型、地理位置、时间要求等特征
3. 系统根据用户标签、信用评分、历史接单情况筛选合适的接单候选人
4. 系统将需求推送给匹配的潜在接单者
5. 用户进入首页可查看系统推荐的相关需求
6. 用户可主动搜索并按类型、距离、报酬等条件筛选需求

#### d.3.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-MATCH-001 | 系统应基于需求类型、地理位置、用户标签自动推荐供需双方 | 中 |
| FR-MATCH-002 | 系统应支持用户按类型、距离、报酬范围、发布时间等条件进行需求检索 | 高 |
| FR-MATCH-003 | 系统应在首页按“最新发布”和“距离最近”两种排序方式展示需求动态流 | 高 |
| FR-MATCH-004 | 系统应向接单者推送可能感兴趣的需求通知（基于历史接单偏好） | 中 |
| FR-MATCH-005 | 系统应支持关键词搜索，并自动联想相关需求 | 中 |

### d.4 特性四：在线沟通

#### d.4.1 说明与优先级

**优先级**：高

供需双方需要通过在线沟通确认细节，是保障互助顺利进行的基础功能。

#### d.4.2 激励/响应序列

1. 接单者点击需求详情页的“联系对方”或“接单”按钮
2. 系统创建双方会话，进入即时通讯界面
3. 双方可发送文字消息、图片、文件进行沟通
4. 系统实时同步消息状态（已发送/已读）
5. 双方可查看对方的基本信息和信用评分

#### d.4.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-CHAT-001 | 系统应提供内置即时通讯功能，支持供需双方在线沟通 | 高 |
| FR-CHAT-002 | 即时通讯应支持发送文字、表情、图片和文件（文件大小限制 50MB） | 高 |
| FR-CHAT-003 | 系统应实时显示消息发送状态（已发送/已送达/已读） | 中 |
| FR-CHAT-004 | 系统应在沟通界面展示对方的信用评分和完成订单数量 | 高 |
| FR-CHAT-005 | 系统应保存聊天记录至少 90 天，供纠纷仲裁时查阅 | 中 |
| FR-CHAT-006 | 用户应可对特定用户进行屏蔽或举报 | 中 |

### d.5 特性五：交易保障

#### d.5.1 说明与优先级

**优先级**：中

针对有偿互助场景，需要提供担保交易机制保障双方资金安全。

#### d.5.2 激励/响应序列

1. 双方确认接单后，需求方支付报酬至平台担保账户
2. 接单方完成任务并确认交付
3. 需求方确认完成，平台将报酬结算给接单方
4. 若发生争议，可申请平台仲裁
5. 交易完成后，双方进行互评

#### d.5.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-TRADE-001 | 系统应支持有偿需求发布时设置报酬金额（0~1000 元） | 高 |
| FR-TRADE-002 | 系统应提供担保支付功能，需求方付款后资金暂存平台，确认完成后再结算给接单方 | 中 |
| FR-TRADE-003 | 系统应记录每笔交易的订单明细，包括金额、时间、双方信息、交易状态 | 高 |
| FR-TRADE-004 | 系统应支持用户查看交易记录和资金流水 | 高 |
| FR-TRADE-005 | 系统应提供交易争议仲裁入口，支持用户提交申诉和证据 | 中 |
| FR-TRADE-006 | 系统应在订单状态变更时（待支付/进行中/已完成/已取消）向双方推送通知 | 高 |

### d.6 特性六：信用评价体系

#### d.6.1 说明与优先级

**优先级**：中

信用评价体系是保障互助质量、约束用户行为的重要机制。通过积分与评价建立信用档案。

#### d.6.2 激励/响应序列

1. 互助任务完成后，系统提示双方进行互评
2. 用户可选择评分（1~5 星）并填写评价内容
3. 系统根据互评结果更新用户的信用积分
4. 系统根据信用积分生成信用等级（如新手/可靠/优秀/卓越）
5. 信用积分和等级影响用户的接单权限、推荐权重等

#### d.6.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-CREDIT-001 | 系统应支持互助完成后双方互评，评分范围为 1~5 星，可附加文字评价 | 高 |
| FR-CREDIT-002 | 系统应根据历史评价和任务完成情况自动计算用户信用积分 | 中 |
| FR-CREDIT-003 | 系统应根据信用积分划分信用等级（至少 3 个等级），不同等级对应不同的平台权益 | 中 |
| FR-CREDIT-004 | 系统应在需求发布、接单等关键环节展示用户的信用评分和等级 | 高 |
| FR-CREDIT-005 | 系统应支持用户查看自己的评价历史和信用积分明细 | 中 |
| FR-CREDIT-006 | 信用积分应关联账号权限，低信用用户应受到接单限制（如每日最大接单量减少） | 中 |

### d.7 特性七：资源共享

#### d.7.1 说明与优先级

**优先级**：低

资源共享模块支持学生上传和分享学习资料、技能教程等，实现知识的无偿流转。

#### d.7.2 激励/响应序列

1. 用户进入资源共享模块，可浏览各类资料列表
2. 用户可按分类、关键词搜索资料
3. 用户可上传资料（文件格式支持 PDF、DOC、PPT 等）
4. 用户可下载/预览他人分享的资料
5. 用户可对资料进行点赞、收藏

#### d.7.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-RES-001 | 系统应支持用户上传学习资料（PDF、DOC、PPT、图片等格式），单个文件限制 100MB | 低 |
| FR-RES-002 | 系统应支持资源按学科、年级、类型等维度分类浏览 | 低 |
| FR-RES-003 | 系统应支持关键词搜索资源 | 低 |
| FR-RES-004 | 系统应支持用户对资源进行点赞、收藏和评论 | 低 |
| FR-RES-005 | 上传资源应通过内容审核（版权和敏感内容过滤） | 中 |

### d.8 特性八：管理员后台

#### d.8.1 说明与优先级

**优先级**：高

管理员后台是平台运营和管理的必要工具，需优先实现核心审核和管理功能。

#### d.8.2 激励/响应序列

1. 管理员登录后台管理系统
2. 管理员可在待审核列表中查看新发布的需求/资源内容
3. 管理员审核通过或拒绝内容
4. 管理员可查看用户列表，进行禁用、警告等操作
5. 管理员可查看纠纷申诉，进行仲裁处理
6. 管理员可查看数据看板，掌握平台运营情况

#### d.8.3 功能需求

| 编号 | 功能需求 | 优先级 |
|------|----------|--------|
| FR-ADMIN-001 | 系统应提供内容审核功能，支持管理员审核需求发布、资源上传等内容 | 高 |
| FR-ADMIN-002 | 系统应提供用户管理功能，支持查看用户信息、禁用/启用账号、查看用户行为记录 | 高 |
| FR-ADMIN-003 | 系统应提供纠纷处理功能，支持管理员查看申诉内容、调取聊天记录和交易记录，做出仲裁决定 | 中 |
| FR-ADMIN-004 | 系统应提供数据看板功能，展示关键运营指标（日活用户、需求发布量、完成率、纠纷率等） | 中 |
| FR-ADMIN-005 | 系统应提供公告管理功能，支持发布系统公告和推送通知 | 中 |
| FR-ADMIN-006 | 系统应记录管理员的操作日志，支持操作审计 | 中 |


## e. 其他非功能需求

### e.1 性能需求

| 编号 | 性能需求 | 指标要求 |
|------|----------|----------|
| NFR-PERF-001 | 响应时间 | 95% 的 API 请求响应时间应小于 500ms；页面首屏加载时间应小于 2 秒 |
| NFR-PERF-002 | 并发处理 | 系统应支持至少 500 个用户同时在线操作，峰值并发请求处理能力不低于 200 TPS |
| NFR-PERF-003 | 消息推送延迟 | 即时通讯消息从发送到送达应小于 500ms |
| NFR-PERF-004 | 数据库查询 | 复杂查询（多条件筛选需求）响应时间应小于 1 秒 |
| NFR-PERF-005 | 文件上传 | 图片上传处理应在 3 秒内完成，大文件上传应提供进度提示 |
| NFR-PERF-006 | 缓存策略 | 热点数据（如首页需求流）应使用 Redis 缓存，缓存更新延迟不超过 1 分钟 |

### e.2 安全需求

| 编号 | 安全需求 | 要求 |
|------|----------|------|
| NFR-SEC-001 | 身份认证 | 必须通过学校统一身份认证完成用户真实性校验，禁止匿名发布需求 |
| NFR-SEC-002 | 数据传输 | 所有客户端与服务器之间的通信必须使用 HTTPS（TLS 1.2+）加密传输 |
| NFR-SEC-003 | 数据存储 | 用户敏感信息（真实姓名、学号、联系方式）必须使用 AES-256 加密后存储 |
| NFR-SEC-004 | 访问控制 | 实现基于角色的访问控制（RBAC），区分学生用户、管理员、系统管理员权限 |
| NFR-SEC-005 | 敏感词过滤 | 所有用户发布的内容（需求描述、聊天消息、评价）应进行敏感词自动过滤 |
| NFR-SEC-006 | 防攻击 | 系统应具备防 SQL 注入、XSS、CSRF 等常见 Web 攻击的能力 |
| NFR-SEC-007 | 隐私保护 | 用户个人信息应遵循“最小必要”原则收集和使用，提供隐私政策和用户授权机制 |
| NFR-SEC-008 | 操作审计 | 关键操作（用户禁用、纠纷仲裁、金额变动）必须记录不可篡改的审计日志 |

### e.3 软件质量属性

| 编号 | 质量属性 | 要求 |
|------|----------|------|
| NFR-QUAL-001 | 可用性 | 系统应保证 99.5% 的服务可用性（每月计划内停机不超过 4 小时，计划外停机不超过 2 小时） |
| NFR-QUAL-002 | 可靠性 | 系统平均无故障时间（MTBF）不低于 720 小时 |
| NFR-QUAL-003 | 可维护性 | 系统应提供完善的日志系统，支持问题追踪和性能分析；核心模块应有完整的接口文档 |
| NFR-QUAL-004 | 可扩展性 | 系统架构应支持水平扩展，可根据用户量增长增加服务节点 |
| NFR-QUAL-005 | 易用性 | 新用户应在 5 分钟内完成首次认证和发布需求的全流程操作；用户满意度不低于 85% |
| NFR-QUAL-006 | 兼容性 | App 应兼容 Android 8.0+ 和 iOS 12.0+ 系统；小程序应兼容微信 7.0+ |
| NFR-QUAL-007 | 数据一致性 | 涉及资金和订单状态的变更必须满足事务一致性要求 |

### e.4 业务规则

| 编号 | 业务规则 |
|------|----------|
| BR-001 | 用户必须完成校园统一身份认证后方可发布需求和接单 |
| BR-002 | 每个用户同时最多发布 10 个进行中的需求 |
| BR-003 | 信用积分低于阈值的用户，每日最大接单量限制为 3 单 |
| BR-004 | 需求发布后可被接单的有效期为 7 天，超期自动失效 |
| BR-005 | 接单后 24 小时内未确认完成，需求方可申请平台介入 |
| BR-006 | 担保支付的报酬在需求确认完成后 48 小时内结算给接单方 |
| BR-007 | 用户对同一笔订单只能进行一次评价，评价后不可修改 |
| BR-008 | 涉及违规行为的用户将被警告、限制功能或永久封禁，具体规则由管理员在后台配置 |
